# Document changes

Turn a set of git changes into correct documentation, and remove the comment
noise that AI-assisted editing leaves behind.

Two deliverables, always in this order:

1. **Code comments and docstrings** in the changed code — cleaned, corrected, and completed.
2. **Prose docs** (README and friends) — updated where the change made them wrong or incomplete.

## Core rules

**Git is the scope, not the subject.** The diff tells you *which* files and
symbols to document. It does not tell you *what to write*. Documentation
describes the current state of the code. It never says "changed", "new",
"updated", "now supports", or "previously". Never add a changelog or a "Recent
changes" section to a README unless the repo already keeps one and the user asks.

**Do not change behavior.** This skill edits comments, docstrings, and prose
only. Do not rename symbols, reorder code, fix bugs, or reformat lines that
carry code. If you find a real bug, note it in your final report and leave it.

**Stay inside the change.** Clean comments in the changed hunks and in the
functions, classes, and files that contain them. Do not sweep the whole repo.

**Never delete machine-readable comments.** These are code, not prose:
`# noqa`, `# type: ignore`, `# pylint: disable`, `//nolint`, `// eslint-disable`,
`#pragma`, `//go:generate`, `// +build`, `@SuppressWarnings`, coverage pragmas,
codegen markers (`Code generated by ... DO NOT EDIT.`), licence and copyright
headers, and `TODO(owner)` / `FIXME(TICKET-123)` items that name an owner or a
ticket.

**Match the repo.** Docstring style (Google, NumPy, Sphinx, Doxygen, Javadoc,
TSDoc), heading depth, tone, and file layout follow what the repo already does.
Read two or three neighbouring files before you write.

## Workflow

### 1. Fix the scope

Use the range the user gave. If they gave none, pick the first that has content:

```bash
git status --short                                  # uncommitted work
git diff --stat && git diff --cached --stat         # unstaged + staged
git log --oneline -10                               # recent commits
git diff --stat $(git merge-base HEAD main)...HEAD  # branch vs base
```

Prefer uncommitted work when it exists. Otherwise use the branch against its
base, and fall back to the last commit. State the range you chose in your
report. Ask the user only when two ranges are both plausible and large.

### 2. Read the change and its context

```bash
git diff <range> -- .        # the change
git diff <range> --name-only # the file list
```

Then read each changed file in full. Diff hunks hide the context you need to
tell a good comment from a bad one. For every changed public symbol, search for
its callers and for any doc that names it:

```bash
rg -n "symbolName" --type-not lock
rg -ln "symbolName" -g '*.md' -g '*.rst' -g '*.txt'
```

### 3. Clean the comments and docstrings

Read `references/comment-hygiene.md` before this step. It holds the removal
taxonomy, the keep list, and worked before/after examples.

The short version:

- Delete comments that narrate the edit, quote the chat, apologise, hedge, or
  restate the code.
- Delete a rationale comment whose only source is a conversation the reader
  cannot see. Either anchor it to something durable — a spec, an RFC, a ticket,
  a benchmark, an upstream bug — or remove it.
- Keep and improve comments that carry non-obvious *why*: invariants, units,
  ordering constraints, workarounds, safety warnings, performance trade-offs.
- Add a docstring to every changed public function, method, class, module, and
  exported type that lacks one. Leave private helpers alone unless they are hard
  to understand.
- Correct docstrings that the change made wrong — stale parameters, stale return
  values, stale exceptions, stale examples.

### 4. Update the prose docs

Read `references/readme-patterns.md` before this step.

Update an existing doc when the change touched: the public API, the install or
build steps, the run commands, configuration, environment variables, defaults,
supported versions, or any behavior the doc describes.

Create a new README only when the change adds a component, package, or service
that has no README and that a reader must run or import. One README per
component. Do not put a README in every directory.

### 5. Write in Simplified Technical English

All generated prose — docstrings and docs both — follows ASD-STE100. Read
`references/ste-writing.md` for the rules and the word substitutions.

The rules that matter most:

- One idea per sentence. 20 words maximum in a procedure, 25 in a description.
- Active voice. Imperative for instructions: "Set the timeout to 30 seconds."
- Simple present tense. Avoid `-ing` forms.
- One word, one meaning. Use the same term for the same thing every time.
- Keep the articles: "the config file", not "config file".
- Six sentences maximum per paragraph.
- No noun stack longer than three words.

### 6. Verify

- Re-read your own diff: `git diff` — confirm every change is a comment,
  docstring, or doc file. No code lines moved.
- If the language has doctests or doc builds, run them: `pytest --doctest-modules`,
  `go vet ./...`, `cargo doc`, `javadoc`, `mkdocs build`, `sphinx-build`.
- Check every command and path you wrote into a doc actually exists.
- Confirm no line you touched lost a linter directive.

### 7. Report

Give the user:

- the git range you documented,
- the files you changed, grouped as *comments cleaned*, *docstrings added or
  fixed*, *docs updated*, *docs created*,
- anything you deliberately left alone and why,
- any bug or inconsistency you found but did not fix.

Keep the report short. Do not repeat the diff back.

## Anti-patterns

Do not do these, even though they look helpful:

| Anti-pattern | Instead |
|---|---|
| A "What changed" section in the README | Describe the current behavior in place |
| A docstring that repeats the type annotations | Describe meaning, units, and constraints |
| A comment above every line | Comment the non-obvious only |
| Deleting every comment you did not write | Judge each one against the keep list |
| Rewriting untouched docs "while you are here" | Stay inside the change scope |
| `# TODO: refactor this later` | Delete it, or file it with an owner |
| Marketing words: "powerful", "seamless", "robust" | State what it does |
